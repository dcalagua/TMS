### 3.2 Backend - `backend/tms-api`

Java 21 + Spring Boot 4.0.7, Maven, with the **official Apache Maven Wrapper 3.3.4**
generated by the wrapper plugin (`distributionType=only-script`, pinned to Maven 3.9.16).
Because the script-only wrapper is used, no `maven-wrapper.jar` binary is committed; the
wrapper fetches the pinned Maven distribution on first use. This resolves baseline blocker
B2 (no global Maven).

Dependencies, all justified, none speculative: Spring Web, Validation, Security, OAuth2
Resource Server, Data JPA, Flyway (+ `flyway-database-postgresql`), PostgreSQL driver,
Actuator, springdoc OpenAPI, and for tests `spring-boot-starter-test`,
`spring-boot-starter-webmvc-test`, `spring-security-test`, ArchUnit. Testcontainers is
deliberately **not** added yet - it belongs to Step 02, where it is first used.

Package boundaries for the modular monolith, each carrying a `package-info.java` that
documents its ownership rather than an empty placeholder class:

    com.ebim.tms.shared          api / config / security infrastructure
    com.ebim.tms.iam             identity, membership, tenancy resolution
    com.ebim.tms.masterdata      origins, zones, destinations, frequencies, routes
    com.ebim.tms.fleet           carriers, vehicle types, vehicles, capacity
    com.ebim.tms.orders          order lifecycle
    com.ebim.tms.planning        trips, assignment, capacity validation
    com.ebim.tms.audit           audit use cases
    com.ebim.tms.integration     external contracts (EWM later, API/events only)

Real code, not scaffolding noise (11 main classes total):

- `TmsApiApplication`;
- `SystemInfoController` + `SystemInfoResponse` - `GET /api/v1/system/info`, the
  public identification/liveness endpoint, plus Actuator `health`/`info`;
- `TmsApiProperties` (validated `@ConfigurationProperties`), `ApplicationConfig`
  (injectable `Clock`), `OpenApiConfig` (contract metadata + bearer JWT scheme);
- `SecurityConfig` + `PublicApiPaths` - stateless, CSRF disabled, no form login or HTTP
  Basic, 401 entry point, a short public allow-list and `anyRequest().authenticated()`.
  **Deny by default from the first commit**; Supabase JWT validation and tenancy
  resolution are Step 03.

Profiles:

- `application.yml` - common configuration, `spring.profiles.default: local`,
  `ddl-auto: none` (Flyway owns schema), `open-in-view: false`, Actuator limited to
  `health,info`, error responses without message/stacktrace;
- `application-local.yml` - local Supabase Postgres defaults
  (`localhost:54322`, throwaway container credentials), every value overridable by
  `TMS_DB_*` environment variables;
- `application-prod.yml` - **no fallbacks**: `${TMS_DB_URL}`, `${TMS_DB_USERNAME}`,
  `${TMS_DB_PASSWORD}` must come from the environment or startup fails fast;
- `src/test/resources/application-test.yml` - Flyway disabled, no external services.

No remote database credential is hardcoded anywhere. `backend/tms-api/.env.example`
carries placeholders only (including the Step 03 Supabase issuer/JWKS entries and an
explicit note that the service-role key is never needed by the backend).

`src/main/resources/db/migration/` exists and is empty apart from a `.gitkeep` that states
the Flyway ownership rule. **No application DDL was written in this step** - that is Step 02.

### 3.3 Frontend - `frontend/tms-web`

React 19 + TypeScript + Vite (`create-vite` `react-ts` template), then adapted:

- React Router 7, Bootstrap 5.3 (CSS + bundle JS), SweetAlert2, TanStack Query,
  React Hook Form. **No MUI.**
- Vitest + Testing Library + jsdom, `globals: false`, explicit cleanup hook.
- TypeScript strictness raised explicitly: `strict`, `noImplicitOverride`,
  `noUncheckedIndexedAccess` on top of the template's `noUnusedLocals`/`noUnusedParameters`.
- Demo assets from the template were deleted rather than left behind.

Structure:

    src/app/        router, providers, TanStack Query client
    src/shared/     typed env, HTTP client, SweetAlert2 helpers, Bootstrap app shell
    src/pages/      DashboardPage, NotFoundPage
    src/test/       test setup

The HTTP client is the enforcement point of the architecture rule: it calls
`VITE_API_BASE_URL` (Spring Boot) only, exposes a `setAuthTokenProvider` seam for the
Supabase session that Step 04 installs, and maps non-2xx responses to a typed `ApiError`
carrying the HTTP status. The dashboard renders the backend identity fetched through it,
so the React -> Spring Boot path is exercised by the shell itself, not only asserted in
prose. `.env.example` contains placeholders and an explicit warning that only the anon key
may ever appear there.
