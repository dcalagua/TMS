# ADR-006 - Proof-of-delivery artefacts go to an object store behind a port, never to the database

- Status: Accepted
- Date: 2026-08-20
- Relates to: `CLAUDE.md`'s "Deferred by decision" list, which names Supabase Storage; ADR-001
  (React -> Spring Boot -> PostgreSQL); ADR-004 (application objects live in `tms`, invisible to
  the Data API).

## Context

Job 05 adds proof of delivery: a signature, a photo of a pallet, a scanned delivery note, attached
to the delivery of one order at one stop (`docs/domain/PROOF_OF_DELIVERY_V1.md`, migration V28).
The delivery *result* is ordinary transactional data and needs no decision. The **bytes** do.

TMS has no file infrastructure. `CLAUDE.md` defers Supabase Storage by decision - correctly, since
nothing before this needed it - and that leaves three ways a feature like this usually gets built,
two of which are mistakes we would not be able to undo cheaply:

1. **Bytes in a column** (`bytea`, or base64 text). A phone photo is 1-5 MB. That is 1-5 MB in
   every backup, every replica, every developer's dump, and in the WAL of a database sized for
   transport rows. It also makes a `SELECT *` on a delivery a multi-megabyte read.
2. **A public bucket with a stable URL.** The artefact is a customer's signature or a photo of
   their loading dock. A permanent public address for it is a data leak that survives deletion of
   the row, is trivially enumerable, and cannot be revoked without breaking every stored link.
3. **Not shipping the feature** until the Storage decision is made - which leaves the delivery
   result with no corroboration for however long that takes, and invites a later implementation to
   pick (1) or (2) under time pressure.

## Decision

Introduce `com.ebim.tms.shared.storage.EvidenceStoragePort`: a small interface with `store`,
`open` and `isEnabled`, and **no method that returns a URL**.

Two implementations ship, selected by `tms.storage.evidence.mode`:

- **`DISABLED` (the default)** - every call raises `EvidenceStorageUnavailableException`, which the
  API answers as `503 storage-unavailable` with a sentence saying that delivery results are still
  recorded without an attachment. A deployment that has not said where a signed delivery note goes
  does not get somewhere guessed for it.
- **`LOCAL`** - `LocalFilesystemEvidenceStorage` writes to a private directory
  (`tms.storage.evidence.root`), laid out as `<companyId>/<yyyy>/<MM>/<uuid>.<ext>`. Appropriate
  for a single node or a container with a mounted volume; explicitly not an answer for two
  instances behind a load balancer.

`tms.delivery_evidence` stores **metadata only**: type, media type, size, SHA-256, and the opaque
key. Bytes are served exclusively by `GET /planning/trips/{id}/deliveries/{deliveryId}/evidence/{evidenceId}/content`,
which is authenticated, company-scoped and permission-checked like every other endpoint, and which
answers `Content-Disposition: attachment` with `Cache-Control: no-store`.

Three invariants every implementation keeps:

1. **The key is generated by the store.** Nothing derived from a caller-supplied file name reaches
   a path - which is what makes traversal not a class of bug here rather than a filter that has to
   be right. `open` re-checks the key's shape and that the resolved path stays under the root.
2. **The store is private.** No signed URLs, no direct-to-bucket uploads, no second access path.
   This keeps the feature inside ADR-001's `React -> Spring Boot -> storage` flow, where the
   permission check lives.
3. **Company first.** Every operation names the tenant, and a key that does not belong to it is
   refused by the store even if it reached that layer.

## Consequences

**Positive.**

- The feature ships now, with the platform decision still open. Adopting Supabase Storage - or S3,
  or anything else - is one more implementation of this interface and **no change to any caller**,
  because the key is opaque and no URL was ever published.
- The two failure modes above are structurally unavailable: there is no content column to fill and
  no URL field to populate.
- A deployment that wants none of it loses only the attachments. The delivery result - who received
  what, when, and why it fell short - is transactional data and is recorded either way.

**Negative, and accepted.**

- `LOCAL` is node-local. A multi-instance deployment must either configure shared storage or leave
  the mode `DISABLED` until the Supabase Storage adapter exists. This is documented rather than
  hidden behind a mode that appears to work and silently loses reads.
- Bytes written before the metadata row can be orphaned if the transaction rolls back. That
  asymmetry is deliberate: a row pointing at an object that was never stored is evidence that
  cannot be produced, while an orphaned object is something a sweep can find.
- Retention and erasure are not solved here. V1 cannot delete evidence at all (the `DELETE` grant
  is withheld), which is the honest interim answer and becomes a real requirement the first time a
  customer asks for erasure. That will need a data-protection decision, and a further ADR.

## Alternatives considered

- **Wait for Supabase Storage.** Rejected: it postpones the whole feature on a decision nobody is
  scheduled to make, and the port makes waiting unnecessary.
- **Store bytes in `tms.delivery_evidence`.** Rejected for the reasons in Context (1); it is also
  the one choice that is expensive to reverse, because the data is already in the database by then.
- **Signed URLs from the application.** Rejected for V1: it needs a store that issues them (we have
  none), and it introduces a second access path whose expiry becomes the security control instead
  of the permission check.
