# ADR-002 - Flyway is the single owner of application schema migrations

- Status: Accepted
- Date: 2026-08-19
- Deciders: TMS by EBIM architecture baseline (Step 00)

## Context

Two migration mechanisms are available:

- **Flyway**, running inside the Spring Boot application (`backend/tms-api`), versioned
  with the backend and applied at startup or by an explicit migrate command;
- **Supabase CLI migrations** (`supabase/migrations`), applied by `supabase db push`
  and generated by `supabase db diff`.

Using both for the same application tables produces two divergent histories, conflicting
version ordering, and drift that is only discovered when a deploy fails or a checksum
mismatch appears. The backend also needs the schema and the code to move together.

## Decision

**Flyway under `backend/tms-api` is the single owner of application schema migrations.**

Flyway owns, for application objects:

- tables, columns, data types;
- primary keys, foreign keys, unique constraints, check constraints, not-null;
- indexes, including GiST indexes for PostGIS columns;
- extensions required by application tables (for example `postgis`, `pgcrypto`);
- **RLS enablement and RLS policies on application tables**;
- database views and any database function the application depends on;
- reference/seed data that is part of the schema contract.

Flyway does **not** own the Supabase-managed `auth` and `storage` schemas. Those remain
managed by Supabase and are never recreated or altered by application migrations.

`supabase/` in this repository holds **local platform configuration only** (for example
`config.toml`, and local-only seed data for a disposable local stack). There is **no**
`supabase/migrations` history duplicating application DDL. If a platform-only migration
directory becomes necessary, it must be documented in this ADR's successor and must not
touch application tables.

**Applied migrations are immutable.** Once a migration has been applied in any
persistent or shared environment, it is never edited or renumbered. Later changes are
new versioned migrations.

## Rationale

1. One history means one source of truth, one ordering and one checksum set.
2. Schema and the code that depends on it version and deploy together.
3. Flyway replay from an empty database is a repeatable test - the basis for the
   Testcontainers migration evidence in later steps.
4. `supabase db diff` generates DDL from a live database; letting it author application
   DDL inverts the direction of truth and encourages ad-hoc changes made in the Studio UI.
5. RLS policies are application authorization artifacts; they must be reviewed in the
   same pull request as the tables and the Java authorization they reinforce.

## Consequences

Positive:

- Deterministic, replayable schema from zero.
- No checksum/ordering conflicts between two tools.
- Migration review happens in the backend repository, alongside the code.

Negative / accepted costs:

- Schema changes made by hand in the Supabase Studio UI are **out of process** and will
  cause drift; the team must not make them.
- Flyway must be granted sufficient database privileges to create extensions and manage
  RLS policies; the migration role is therefore more privileged than the runtime role.

## Compliance rules

- No `supabase/migrations` directory containing application DDL.
- No application DDL executed manually against a shared database.
- No edits to an already-applied migration file; add a new versioned migration.
- Migration replay against a disposable PostgreSQL/PostGIS instance is the acceptance
  evidence for every schema step.
- The Supabase-managed `auth` and `storage` schemas are read-only from Flyway's
  perspective (referencing `auth.users` by id is allowed; altering it is not).

## Alternatives considered

- **Supabase CLI migrations as owner**: rejected - decouples schema from backend code,
  encourages UI-authored drift and makes replay-in-tests awkward.
- **Both tools, split by concern**: rejected - the split is impossible to police in
  practice; RLS policies and tables would end up in different histories.
- **Liquibase**: viable, but Flyway's plain-SQL versioned files are simpler to review
  and are the default in the Spring Boot ecosystem. No advantage justified the switch.
